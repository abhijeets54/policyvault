🧠 AI Extraction Pipeline — Deep Dive

What You Currently Have

Your primary extractor (src/lib/ai/extractor.ts) uses Groq Llama 4 Scout as the primary engine with pdf-parse to get text, then Gemini 2.5 Flash as the fallback using native PDF understanding (multimodal). Duplicate extraction modules: extract.ts and extractor.ts both exist and serve overlapping purposes. The route uses extractor.ts but the old file is never cleaned up. This is a maintenance and confusion risk.

🚨 Current Pipeline Problems

1. Scanned PDFs Are Completely Broken

The Groq path uses pdf-parse which can only extract text from digitally-created PDFs. Any scanned insurance policy (the majority of old policies in India) returns blank text, meaning Groq extracts nothing and you get an empty result or fall back to Gemini.

Indian insurance agents frequently deal with scanned copies. This is a near-total failure mode.

2. Fallback Threshold is Too Low

The score() function in the legacy extractor approves a Gemini result if it gets ≥ 3 fields. A result with holder_name, policy_number, and insurer_name only would pass even if it missed all financial data and dates.

Fix: require at minimum holder_name + policy_number + expiry_date (the critical triad) to be non-null.

3. No Cross-Validation

There is zero comparison between what Gemini and Groq return. If both models agree on the same wrong value for a field, you never know. For a SaaS where agents trust the AI output, this is dangerous.

Solution: Run both models in parallel, compare key fields, flag discrepancies for human review, and boost confidence score when they agree.

4. Groq Text Truncation

The Groq extractor truncates text to 20,000 characters. A 30-page group health policy or a complex life insurance document will easily exceed this, causing critical data (nominee, riders, annexures) to be cut off silently.

Fix: Use Gemini 2.5 Flash (1M token context, native PDF) for long docs, with chunking strategy for Groq fallback.

5. No Retry Logic

If Gemini returns a malformed JSON or hits a rate limit, the whole extraction fails. There's a try-catch but no exponential backoff or retry. In production with multiple agents uploading simultaneously, this will cause silent failures.

Fix: Add 2-3 retries with exponential backoff using a utility like p-retry.

6. No Prompt Versioning / A-B Testing

The extraction prompt is hardcoded in the source. If you update it, you can't compare new vs old accuracy. As you scale and encounter edge cases (LIC policies, Bajaj Allianz formats, etc.), you need to iterate the prompt without breaking existing extractions.

Fix: Store prompts in a table with versions; test new prompts against saved sample PDFs before deploying.

✅ Recommended New Pipeline Architecture

/**
 * UPGRADED EXTRACTION PIPELINE (3-tier with cross-validation)
 * 
 * Tier 1: Gemini 2.5 Flash — always runs first (native PDF, handles scanned)
 * Tier 2: Claude Haiku 4.5 — parallel run for validation (text PDFs)
 * Tier 3: Groq Llama 4 Scout — emergency fallback if both fail
 * 
 * Cross-validation: compare key fields between models
 * Confidence boost: if both models agree → "high"
 */

export async function extractPolicyFromPDF(pdfBuffer: Buffer): Promise<ExtractionResult> {
  
  // Always run Gemini (handles both text and scanned PDFs)
  const geminiPromise = extractWithGemini(pdfBuffer).catch(e => ({ error: e.message }))
  
  // Run Groq in parallel for text-based PDFs (free, fast)
  const groqPromise = extractWithGroqText(pdfBuffer).catch(e => ({ error: e.message }))
  
  const [geminiResult, groqResult] = await Promise.allSettled([geminiPromise, groqPromise])
  
  // Cross-validate: if both succeed, merge with confidence boost
  if (geminiResult.status === 'fulfilled' && groqResult.status === 'fulfilled') {
    return mergeAndValidate(geminiResult.value, groqResult.value)
  }
  
  // Single model succeeded
  if (geminiResult.status === 'fulfilled') return geminiResult.value
  if (groqResult.status === 'fulfilled') return groqResult.value
  
  // Emergency: both failed, try Claude Haiku (paid)
  return extractWithClaude(pdfBuffer)
}

// Cross-validation: flag fields where models disagree
function mergeAndValidate(a: ExtractedPolicyData, b: ExtractedPolicyData) {
  const CRITICAL = ['expiry_date', 'sum_insured', 'premium_amount', 'policy_number']
  const conflicts = CRITICAL.filter(f => a[f] && b[f] && a[f] !== b[f])
  return {
    ...a,
    extraction_confidence: conflicts.length === 0 ? 'high' : 'medium',
    extraction_notes: conflicts.length ? 
      `Models disagreed on: ${conflicts.join(', ')} — please verify` : a.extraction_notes,
    cross_validated: true,
    model_agreement: conflicts.length === 0
  }
}

🐛 Bugs, Problems & Dangers Found

CRITICAL

🔴 CRITICAL #1 — Monthly Cron Email Never Works (401 Always)

File: src/app/api/cron/monthly/route.ts

The route calls createClient() (session-based Supabase client) and immediately checks supabase.auth.getUser(). The pg_cron job at supabase/cron.sql sends only the x-cron-secret header — no auth cookie, no JWT token. Result: getUser() returns null, route returns 401, and the monthly email has never been sent automatically since the app launched.

Additionally, the route only emails the "current user" (which doesn't exist in a cron context). The README says it should enumerate all agents — the code doesn't do this at all.

✅ Fix: use createAdminClient() + verify x-cron-secret header first, then iterate all active profiles using the service role client. 
// CORRECT pattern for cron route:
export async function POST(req: NextRequest) {
  // Step 1: Verify cron secret (replaces auth check)
  const secret = req.headers.get('x-cron-secret')
  if (secret !== process.env.CRON_SECRET) {
    return NextResponse.json({ error: 'Forbidden' }, { status: 403 })
  }
  
  // Step 2: Use admin client to bypass RLS
  const admin = createAdminClient()
  
  // Step 3: Get ALL active users from profiles
  const { data: agents } = await admin
    .from('profiles')
    .select('id, email, full_name')
    .eq('is_active', true)
  
  // Step 4: For each agent, fetch their policies and send email
  for (const agent of agents ?? []) {
    const { data: policies } = await admin
      .from('policies')
      .select('*')
      .eq('user_id', agent.id)
      .gte('expiry_date', startDate)
      .lte('expiry_date', endDate)
    // ... send email to agent.email
  }
}

🔴 CRITICAL #2 — Scanned PDFs Return Empty Extraction

File: src/lib/ai/extractor.ts

The primary extraction path uses pdf-parse which only reads text-layer data from digitally-created PDFs. Scanned/photographed insurance PDFs return an empty string, causing Groq to receive blank input and hallucinate or return all-null fields. The Gemini fallback only triggers if the score is below threshold — if Groq returns a few hallucinated fields (score ≥ 3), Gemini is never called.

Indian insurance agents regularly scan physical policies. This is a complete data-loss failure mode.

✅ Fix: Always run Gemini first (it handles scanned PDFs natively). Use pdf-parse only to check if text is present; if text length < 100 chars, skip Groq entirely.

🟠 MAJOR #4 — Duplicate Extraction Modules in Production

Files: src/lib/ai/extract.ts AND src/lib/ai/extractor.ts

Two extraction orchestrators exist simultaneously with different model order (Gemini-first vs Groq-first). The route uses extractor.ts but extract.ts is still imported in potentially other places. Comments call it "legacy" but it isn't deleted. This creates confusion, inflates bundle size, and is a maintenance hazard if someone fixes a prompt bug in the wrong file.

✅ Fix: Delete src/lib/ai/extract.ts, src/lib/ai/gemini.ts, and src/lib/ai/groq.ts after consolidating all logic into extractor.ts.

🟠 MAJOR #5 — No Indexes on Critical Columns (Performance)

File: supabase/schema.sql

The schema creates the policies table but no indexes are defined on the most-queried columns: user_id, expiry_date, policy_type, status, and holder_name. With even 500 policies per agent and 10 agents, every filtered query (monthly register, search, expiry alerts) will do a full sequential scan.

✅ Fix: Add indexes in schema.sql or as a migration. 
CREATE INDEX IF NOT EXISTS idx_policies_user_id ON policies (user_id);
CREATE INDEX IF NOT EXISTS idx_policies_expiry_date ON policies (expiry_date);
CREATE INDEX IF NOT EXISTS idx_policies_user_expiry ON policies (user_id, expiry_date);
CREATE INDEX IF NOT EXISTS idx_policies_status ON policies (status);
CREATE INDEX IF NOT EXISTS idx_policies_type ON policies (policy_type);
MAJOR

🟠 MAJOR #6 — In-Memory Rate Limiter is Effectively Broken on Vercel

File: src/app/api/extract/route.ts (implied)

The README acknowledges this but it's worth classifying as Major, not just a caveat. On Vercel's serverless (hobby plan), functions spin up cold for every request or are distributed across multiple instances. An in-memory rate limiter resets on every cold start and doesn't coordinate across instances. An agent could upload 100 PDFs in quick succession and hit Gemini API 100 times, running up significant costs or exhausting your free tier.

✅ Free Fix: Use Supabase to store rate limit state (a simple rate_limits table with user_id + request_count + window_start). Paid: Upstash Redis (~₹0/month on free tier up to 10k req/day).
MAJOR

🟠 MAJOR #7 — xlsx Package Has Known Vulnerabilities (SheetJS CE)

File: package.json — "xlsx": "^0.18.5"

SheetJS CE (the open-source version) at 0.18.x has known prototype pollution and ReDoS vulnerabilities (CVE-2023-30533). The package is also no longer receiving security updates on npm. For a SaaS handling financial data, this is unacceptable.

✅ Fix: Replace with exceljs (actively maintained, full-featured) or use SheetJS Pro if budget allows. Alternatively, use Supabase Edge Functions for server-side export.
MINOR

⚠️ MINOR #8 — No Content-Security-Policy Nonce (XSS Risk)

CSP has 'unsafe-inline' and 'unsafe-eval' in script-src. While Next.js 14 requires these for hydration, the recommended approach is to use CSP nonces with Next.js's built-in nonce support. Without nonces, a stored XSS vulnerability in any policy text field could execute scripts.

✅ Fix: Implement CSP nonces via Next.js middleware. See: Next.js CSP docs.
MINOR

⚠️ MINOR #9 — No CRON_SECRET Validation in the Route

The middleware.ts exempts /api/cron/* from auth redirects. But if an attacker knows your API URL and hits /api/cron/monthly without auth, the current code returns 401 (because getUser returns null). However, once you fix Bug #1 by removing the user check, the route becomes unauthenticated unless you explicitly verify the cron secret header. This must be implemented as part of the Bug #1 fix.

✅ Fix: First line of fixed cron route: verify x-cron-secret header matches process.env.CRON_SECRET, return 403 if not.
MINOR

⚠️ MINOR #10 — No Auto-Status Update for Expired Policies

The status column on policies is set to 'active' and presumably stays there forever unless an agent manually changes it. A policy whose expiry_date has passed should automatically show as 'expired'. The dashboard currently shows all 'active' policies including ones that lapsed years ago, giving agents a false view.

✅ Fix: Either (a) compute status dynamically via a DB view using CASE WHEN expiry_date < NOW() THEN 'expired' ELSE status END, or (b) add a pg_cron job that runs daily to update expired policies.
MINOR

⚠️ MINOR #11 — Vercel maxDuration: 60 May Not Be Enough

The extract route sets maxDuration = 60 seconds. On the Vercel Hobby plan, the maximum is 60s. However, Gemini 2.5 Flash processing a complex 40-page policy PDF + pdf-parse + retry logic can easily take 50-55s, leaving little headroom. Any network hiccup causes a timeout.

✅ Free Fix: Use Vercel Pro (₹1,500/month) for 300s functions, or better: move extraction to a background job pattern using Supabase Edge Functions + a queue table (Supabase already has pgmq extension support).

🔵 INFO #12 — Groq SDK Version Outdated

"groq-sdk": "^0.9.0" — Groq SDK is at v0.14+ as of mid-2026 with significant API improvements. The Llama 4 Scout model string in your code (meta-llama/llama-4-scout-17b-16e-instruct) may also have changed.

🔒 Security Analysis

What's Already Good ✅

Supabase RLS

Row Level Security is enabled on the policies table with auth.uid() = user_id policies. This is the single most important thing and you have it right. Even if an agent's token is stolen, they can't access another agent's data.

Storage Scoping

Storage bucket is private with auth.uid()-scoped policies. The extract route also validates that the pdfPath starts with user.id/ before generating a signed URL. Good defense-in-depth.

Signed URLs (30 min)

PDFs are served via time-limited signed URLs rather than public links. 30 minutes is a reasonable window. The approach of not storing public URLs and generating signed URLs on demand is correct.

Service Role Key Isolation

The SUPABASE_SERVICE_ROLE_KEY is only used in server-only files (src/lib/supabase/admin.ts) and never exposed to the client. This is critical and is done correctly.

Security Headers

X-Frame-Options, X-Content-Type-Options, HSTS, Referrer-Policy, Permissions-Policy are all set in next.config.js. This is a solid baseline.

No Public Sign-Up

Supabase Auth is configured to disable public sign-ups. New agents are only created by admins. This is correct for a B2B SaaS where you control who has access.

Security Gaps to Fix 🚨

MAJOR

No Audit Log Table

There's no record of who uploaded which PDF, when data was changed, or which agent accessed what. For an insurance SaaS handling sensitive PAN, DOB, and policy data, audit logs are essential for compliance (DPDP Act 2023 in India, IRDAI data protection guidelines) and for debugging disputes.

✅ Fix: Add an audit_logs table and PostgreSQL trigger to log all INSERTs/UPDATEs/DELETEs on the policies table. 
CREATE TABLE audit_logs (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id UUID NOT NULL,
  action TEXT NOT NULL, -- 'upload' | 'edit' | 'delete' | 'export' | 'view_pdf'
  resource_type TEXT NOT NULL DEFAULT 'policy',
  resource_id UUID,
  metadata JSONB,
  ip_address TEXT,
  created_at TIMESTAMPTZ DEFAULT now()
);
ALTER TABLE audit_logs ENABLE ROW LEVEL SECURITY;
-- Agents can only see their own logs
CREATE POLICY "own_logs" ON audit_logs FOR SELECT USING (auth.uid() = user_id);
MAJOR

No MFA / 2FA Support

The app uses email/password only with no MFA option. Insurance agents access sensitive PAN numbers, DOBs, and policy data of clients. A compromised agent account exposes all their clients' data. Supabase Auth supports TOTP (Authenticator app) and phone OTP natively.

✅ Fix: Enable Supabase MFA in Authentication settings. Add a TOTP enrollment flow in the agent's settings page. Consider making MFA mandatory for agents handling sensitive data.
MAJOR

Sensitive Data in Plain Text (PAN, DOB)

The holder_pan field stores PAN numbers in plain text in the database. PAN is classified as sensitive personal data under India's DPDP Act 2023. If the database is ever compromised, all PANs are exposed. Same concern for holder_dob and holder_phone.

✅ Fix (Free): Use Supabase Vault's pgsodium extension to encrypt these columns at rest. Alternatively, use application-level encryption before inserting (AES-256-GCM with a KMS-managed key stored in Supabase Vault).
MINOR

WAHA API Keys in .env.example but Not Used

Your .env.example includes WAHA_API_URL, WAHA_API_KEY, and WAHA_SESSION_NAME. If these are populated in the actual deployment environment but WAHA isn't implemented, this is dead code creating a false security surface. Also, WhatsApp Business usage has strict data processing restrictions.

✅ Fix: Remove WAHA env vars from .env.example entirely if not used. Document them separately when you add the WhatsApp feature.
MINOR

No CSRF Protection on State-Changing API Routes

POST/PUT/DELETE API routes rely on Supabase auth validation but have no explicit CSRF token validation. While Supabase's cookie-based auth provides some inherent CSRF protection (SameSite cookies), a belt-and-suspenders approach with a CSRF token header is recommended for a SaaS.

✅ Fix: Add a custom header check (X-Requested-With: XMLHttpRequest) or use the double-submit cookie pattern. Next.js route handlers are inherently CORS-protected but not fully CSRF-safe.
INFO

PDF File Type Validation (Client-Side Only)

The upload component uses react-dropzone with an accept prop that restricts to PDF. But this is purely client-side. The server route doesn't validate the MIME type of the uploaded file. An attacker could upload a malicious file disguised as a PDF.

✅ Fix: In the extract route, after downloading the PDF buffer, check the magic bytes: buffer.slice(0,4).toString() === '%PDF'. Reject anything that doesn't start with PDF magic bytes.

IRDAI & DPDP Compliance Checklist

Insurance data in India falls under IRDAI's data protection circular (2023) and the Digital Personal Data Protection Act (DPDP) 2023. Before going commercial, ensure:

  • Privacy Policy: Publish a clear privacy policy explaining how policyholder data is stored and used.
  • Data Retention Policy: Define how long policy data is kept after an agent's subscription ends.
  • Right to Erasure: Ability to delete all data for a specific agent/their clients on request.
  • Data Processing Agreement: With Supabase (they offer a DPA) and Vercel for the EU/India data residency requirement.
  • Consent: Agent must confirm they have consent from policyholders to store their data.
  • Breach Notification: Process for notifying affected users within 72 hours of a breach.
  • Supabase Region: If storing Indian data, consider Supabase's Singapore or Mumbai region for data residency.

⚡ Feature-by-Feature Upgrade Analysis

1. Upload & Extraction Flow

📤

Current: Single PDF upload → AI extract → Review form → Save

What works: The mandatory verification step before saving is excellent design — agents must confirm AI output before it's stored. The Supabase Storage direct upload (bypassing Vercel's 4.5MB limit) is a smart architectural choice.
What to improve: Add bulk upload (multiple PDFs at once), a drag-and-drop queue with progress indicators, extraction retry without re-uploading, and a preview pane showing the PDF alongside the extraction form side-by-side.

2. Policy List & Search

🔍

Current: Filter by type/status, text search on name/number, pagination

What works: Server-side pagination and filtering via the API route is correct — never load all policies client-side.
Issues: The search uses ilike.%term% which is a full table scan for each character typed. No debounce visible in the code. For an agent with 2,000 policies, this will be slow.
Fix: Add a PostgreSQL Full Text Search index on holder_name || ' ' || policy_number || ' ' || holder_phone. This turns the search from a scan to an index lookup. Also add client-side debounce (300ms).

3. Expiry Register (Monthly Export)

📊

Current: ExpiryBanner on dashboard, download Excel/PDF for current month, automated cron email

What works: The concept is excellent — an insurance agent's most critical workflow is the monthly renewal chase.
Issues: (1) The cron email is broken (see Bug #1). (2) The banner only shows for days 1-7 of the month — agents may miss renewals that fall in the last week of the month unless they check manually. (3) The Excel export uses the broken xlsx package (see Bug #7). (4) No ability to select a custom month/year range for export.
Improvements: Fix cron, add 7/15/30-day lookahead expiry alerts not just monthly register, add WhatsApp reminder to client (with their consent).

4. Policy Detail Page

📄

Current: View all extracted fields, edit, delete, view PDF via signed URL

What works: Signed URLs for PDF viewing are correct. Edit/delete with ownership verification is good.
Missing: Renewal history (when did this policy get renewed last?), renewal reminder status (was this policy in last month's email?), a "Mark as Renewed" button that auto-creates the next year's policy record with date incremented, client communication log, and sharing a policy summary with the client via email/WhatsApp.

5. PWA (Progressive Web App)

📱

Current: Service worker, manifest, installable from Chrome/Safari

Issues: Manifest references wrong paths (see Bug #3). Push notifications are not implemented — this is a significant gap for a PWA used for insurance renewals. No offline mode for viewing previously loaded policies.
Improvements: Add Web Push Notifications for expiry alerts (free via Supabase Edge Functions + a push service like Web Push library). Add offline cache for the policy list. Add home screen shortcuts for "Upload Policy" and "This Month's Expiries".

6. Authentication & User Management

🔐

Current: Email/password only, admin creates users via script

Issues: No MFA, no password reset UI (Supabase handles this but is it wired up?), no agent self-service profile editing, no activity log for admins to see what agents have uploaded.
For SaaS: You need a self-service signup flow with email verification, subscription plan selection, payment gateway integration, and agent-level admin dashboard to manage their account. The current "admin creates users manually" model is unsustainable at scale.

2. Auto-Status Update for Expired Policies

-- Create a view that computes current status dynamically
CREATE OR REPLACE VIEW policies_with_status AS
  SELECT *,
    CASE
      WHEN expiry_date < CURRENT_DATE AND status = 'active' THEN 'expired'
      ELSE status
    END AS computed_status
  FROM public.policies;

-- Or: daily job to auto-expire
SELECT cron.schedule(
  'auto-expire-policies', '0 1 * * *',
  $$UPDATE public.policies 
    SET status = 'expired', updated_at = now()
    WHERE expiry_date < CURRENT_DATE AND status = 'active'$$
);

// src/lib/rate-limit.ts
import { Ratelimit } from '@upstash/ratelimit'
import { Redis } from '@upstash/redis'

export const extractRatelimit = new Ratelimit({
  redis: Redis.fromEnv(), // UPSTASH_REDIS_REST_URL + TOKEN in .env
  limiter: Ratelimit.slidingWindow(10, '1h'), // 10 extractions per hour per user
  analytics: true,
})

// In /api/extract/route.ts:
const { success, reset } = await extractRatelimit.limit(user.id)

  )
}
